# 12 · QA: how to verify without lying to yourself

This file exists because our QA once passed while the site was broken. Almost every failure we have shipped was
**silent**: the site answered 200, looked fine in the check we ran, and was broken for real visitors. Two rules sit
above everything else:

- **A check that cannot fail is not a check.** Pair every signal with an independent one: status plus content type
  and size; crawl plus index; visual pass plus static lint.
- **When production behaves differently from local, look at production before changing code.** When the client says
  it is broken and `curl` says it is fine, render the live URL in a real browser before touching a line.

---

## The audit: one command, every automatable item

Our toolkit has one audit command for every client site. It reads the site's output folder and the generator's
constants (without running the generator), serves the output locally, drives a headless browser over it, and with a
flag does the same against the live domain. **It exits 1 when a gate fails**, so the deploy command can refuse to
ship. The source is internal; this is what it checks, so you can build your own.

| Item | How it is checked |
|---|---|
| Titles, descriptions | length (title ≤ 60, 62 hard max; description ≤ 158) and uniqueness; ads landings and deliberate noindex pages excluded |
| H1 and headings | exactly one H1, first; no heading level jumps, footer included |
| Canonical, language | canonical = domain + path; `lang` (and `en` under `/en/`); viewport, charset, theme-color; `hreflang` targets exist, are reciprocal and have `x-default` |
| Social card | og + twitter tags present; `og:image` absolute, JPG/PNG, opened and measured at 1200x630; one per page |
| Breadcrumbs, schema | visible breadcrumbs match `BreadcrumbList` names; JSON-LD parses; FAQ questions and answers visible on the page; no `Product`/`Offer` without a price |
| Images, links | alt present and descriptive; width and height; every internal link resolves (files, folders, redirect sources, `#ids`); `_blank` has `noopener`; two or more pages link to every page |
| WhatsApp links | every `wa.me`, `api.whatsapp.com` and data-attribute link carries a message; emoji only with `api.whatsapp.com`; not the site-wide message alone |
| Copy rules | em and en dashes (text, alt, meta, JSON-LD), hashtags, negative phrasings, struck-through prices; "missing", "pending", "demo", lorem, template brackets and placeholder boxes (a failure once indexable, a warning during review) |
| Weight | HTML over 150 KB, page over 1.5 MB before lazy images; any third-party request beyond analytics, session recording and the map |
| 404 | the page exists with a link home, WhatsApp and the site's CSS; the Worker uses the 404 page; live, an unknown URL answers 404 (**gate**) |
| robots, sitemap | robots by mode; legal paths disallowed in **every** group; sitemap only when indexable, equal to the indexable pages, with lastmod; live, every `<loc>` 200 and indexable |
| Icons, headers | `favicon.ico`, 32 px PNG, apple-touch-icon; nosniff and referrer policy; every asset either cached a week or more with a versioned URL, or `immutable` with a hash |
| Local schema, FAQ | `LocalBusiness` with address, phone, geo, hours, `sameAs`; the phone visible on the home and contact; five or more FAQs |
| Legal pages | exist, noindex, no template brackets, not in sitemap or `llms.txt`, disallowed everywhere, linked from every page (**gate**) |
| Ads landings | noindex, no navigation, only WhatsApp and call links, their own message |
| **Sideways scroll** | headless browser at 360, 375, 390 and 430 px, clipping off, a slow scroll sampling every 60 ms for anything past the right edge, closed `<details>` and menus measured open (**gate**) |
| Fonts, images | local woff2, no font CDN, preload with `crossorigin`, metric fallback, the currency glyph in the body font (read with fontTools); content photos WebP with three `srcset` widths and `sizes`, lazy, hero preloaded, no EXIF/GPS |
| Accessibility | a `<main>`, labelled icon-only controls, a visible focus outline; **measured at 390 px**: AA contrast of every text against what is actually painted under it (colour-space aware), controls under 44 px |
| CSS hygiene | `[hidden]{display:none!important}` present; no state class (`in`, `on`, `open`, `play`) or single-use modifier also styled on its own |
| Frozen pages, console | every page answers a debugger ping and draws frames; console errors and failed requests |
| Tracking | analytics and session-recording IDs in the generator and on every page; tags behind the host guard, deferred, Do Not Track honoured when promised; the IDs register row |
| Live = build | every page live equals the build (email obfuscation normalised); robots.txt equals the build's |
| Index mode | while noindex: every page noindex, live too. Indexable: no noindex outside 404, legal and declared exceptions; the canonical host detached from the header; preview hosts 301 or noindex; the launch go recorded (**gate**) |
| Redirects and cache | www and http → https apex, 301, path and query kept; the third request of a page is `HIT` |
| On request | Search Console property and sitemap by API; IndexNow key live; GA4 and Clarity collect requests seen live; Lighthouse mobile 3 runs median on the home and two key pages |

Timings we measured: static checks alone about 1 second; the local browser pass about 85 seconds (11 templates at 4
widths); with the live domain 1.5 to 3.5 minutes; Lighthouse adds 5 to 8. The browser pass can be skipped for speed
**but never before a deploy**: the sideways-scroll probe is a gate.

**What the audit cannot check, so a person does:** the primary action visible in the first screen; every claim
traceable to the client; no staff names unless asked; copy approved by a human; the bottom bar and WhatsApp on every
screen; the contact block written identically everywhere; reviews real and verbatim; no loader, cursor effect or
autoplaying raw video; above the fold painted, not revealed; the motion budget; photos framed without bars or cuts;
nothing to maintain; the anti-generic fingerprint; events on clicks only; no personal data in events.

## QA before every deploy, not once

1. The audit exits 0 (no gate open), run **with** the browser pass.
2. Real-viewport captures at 1440x900 and 390x844 of every changed page, **looked at**. Half of the errors we found
   across twenty demos were visual, not technical: a headline that wraps to three lines, text unreadable on its
   background, the demo badge covering a button.
3. Console errors 0, link crawl 0 broken, every form and builder exercised end to end.
4. **After any change of a hard fact** (phone, address, hours, price, material, origin): grep every variant across the
   generator and the output, schema and share cards included. A number that appears in one place appears in four: one
   correction turned out to be four paragraphs on two pages plus a spec table. If the phone changed, the uptime keyword
   changes in the same step.
5. Nobody else is working on the site, and the new build was diffed against live.
6. After the deploy: status + content type + size on the changed URLs, purge done, `HIT` after.

## The probes worth building

### Sideways scroll on phones (a launch gate)
Load the page at 360, 375, 390 and 430 px, scroll slowly to the bottom, and every 60 ms compare
`document.documentElement.scrollWidth` with the viewport and list any element whose right edge passes it. Open every
`<details>` and menu first. In a browser console:

```js
// paste at a phone width; lists what sticks out past the right edge
(() => {
  document.querySelectorAll('details').forEach(d => (d.open = true));
  const W = document.documentElement.clientWidth, out = new Map();
  for (const el of document.querySelectorAll('body *')) {
    const r = el.getBoundingClientRect();
    if (r.width && r.right > W + 1) out.set(el, Math.round(r.right - W));
  }
  console.log('scrollWidth', document.documentElement.scrollWidth, 'viewport', W);
  console.table([...out].slice(0, 30).map(([el, px]) => ({ el: el.tagName + '.' + el.className, px })));
})();
```

Usual culprits: an animation library's start state with a large scale near the edge (applied at load), a fixed grain
layer with negative inset, rotated badges, `width: 110%` decorations, a drawer parked with `translateX(100%)` (add
`visibility:hidden` when closed), a long word in a table cell, `repeat(auto-fit, minmax(Npx, 1fr))` with N too big.
The net is `overflow-x: clip` on the section that owns the effect and on `html` (prefer `clip` to `hidden`: `hidden`
on `body` breaks `scrollTo` and lazy loading in tests). Known false positives: a rail that scrolls sideways on purpose
always reports items off screen; the first samples of a load (under about half a second) can catch the unstyled first
paint, so re-run: a real overflow repeats with the same few pixels.

### A frozen page
Symptoms: no `load` event, a debugger `Runtime.evaluate` that never answers, a headless screenshot that is never
written while a script-free copy of the same page renders in seconds. One live site froze in every browser because of
an infinite `while (root.firstChild)` loop that used `importNode` (which copies the node instead of moving it). Three
rounds of "headless hangs on this page, work around it" hid a bug the client was hitting on his phone. **When a
headless render stalls, probe before building a workaround**: over the DevTools protocol, check that load fired, ping
`Runtime.evaluate`, then per scroll position read renderer CPU (`Performance.getMetrics`), style recalculations,
layouts and animation-frame times, with animations running and paused. Hard timeouts everywhere and kill the whole
process tree on exit. If the ping times out, bisect the scripts. The same probe showed a looping CSS transform on an
SVG costing a layout per frame.

### Contrast and tap targets, measured
At 390 px, for every text node, compare its colour with what is actually painted under it (walk up to the first
opaque background, account for images and gradients, handle modern colour spaces such as `oklch`), and flag anything
under WCAG AA. Flag any interactive element smaller than 44 px. WhatsApp green carries dark text.

### Real-viewport captures
Fix the viewport over the DevTools protocol (`Emulation.setDeviceMetricsOverride`) at 1440x900 and 390x844, capture
at several scroll offsets, and add `?v=N` to the URL after a redeploy (the browser profile caches). To capture an
interactive state, run a snippet first that clicks the options. CDP screenshot clips are in page coordinates: add
`scrollY`. Wait for visible images to be `complete` first.

## Headless browsers: the traps

- **Forcing reduced motion makes the page look perfect** while the real page is broken: that CSS branch reveals
  everything and forces stroke offsets to zero. The static animation lint catches what the visual pass cannot.
- **Headless browsers do not fire `IntersectionObserver` below the fold** under a virtual time budget, so the page
  renders truncated at `opacity: 0`. Two ways out: force reduced motion to see the static state, or put the page in a
  very tall iframe inside a QA wrapper (`<iframe src="page.html" width="1440" height="18000" scrolling="no">`): the
  observer sees everything in view and the whole page reveals and animates.
- **Some headless builds ignore `--window-size` for layout width**: they lay out at about 500 px and crop to the width
  you asked for, which looks exactly like overflow. It is not. Use a 375 px iframe, or the device-metrics override.
- **Under a virtual time budget `setTimeout` fires but CSS transitions do not resolve**, so anything gated on a
  transition end never completes there.
- **Read a copy of the render output**, not the file itself, or you may be looking at a cached version. Ours was
  genuinely stale and the copy proved it.
- **Launch each headless instance with its own free debugging port and its own profile directory**, and kill the
  process tree when done; hung instances poison later runs and can keep writing their profile folder after you delete
  it. On one machine the newer headless mode died while another instance was open; the old mode worked. On macOS one
  Chromium build's `--screenshot` flag hung: capture over the DevTools protocol instead.
- **A Google Maps iframe never paints in headless.** Prove it loaded instead: reading its
  `contentWindow.location.href` must throw `SecurityError` (cross-origin means a real document loaded; `about:blank`
  means it is broken), and the resource timing must list the maps request.
- **Automation panes inside apps:** when hidden they report `innerWidth` 0 (and then every width you measure is
  garbage), do not fire observers, throttle frames to about 2 per second, never load lazy images, and buffer console
  messages from the previous page. Open a fresh tab per check, read the DOM rather than screenshots, and never judge
  motion or layout there. A `requestAnimationFrame` loop guarded by a "pending" flag stays dead forever in a hidden pane,
  frozen at a plausible value.
- **`naturalWidth === 0` does not mean the image is broken**: a valid WebP showed it on a pane's first render. Load it
  manually with `new Image()` and a cache-buster before hunting. Lazy images must be measured after a scroll sweep.
- **Strip the query string before resolving links against disk**, or every versioned asset reports as missing.
- **Read the CSSOM** to rule out "my CSS is not applied" instead of guessing from the source.
- **To confirm a phone fix did not touch desktop, compare the resolved values**, not the CSS.
- **Removing a component means sweeping three layers** (markup, CSS, JS): grep every identifier it used, in the source
  and in the deployed HTML.
- `innerText` returns uppercase for elements with `text-transform: uppercase`: a lowercase search reports "not rendered".

## Delivery audit

Before writing a single line of the delivery document: the proposal PDF, the calendar and the per-site checklist,
checked against the **live** site, by curl and by eye. One delivery audit found nine gaps nobody had seen. Fix ours
first.

## Checklist · quality

- [ ] The audit exits 0 with the browser pass; the failing non-gate items listed with who they wait on.
- [ ] Captures at 1440 and 390 of every changed page, looked at: H1 on two lines or fewer on a phone, primary action
      visible, nothing cut, text readable on its background.
- [ ] No sideways scroll at 360, 375, 390, 430 (menus and accordions open).
- [ ] Contrast AA measured; tap targets 44 px; `aria-label` on icon-only buttons; a `<main>`; visible focus.
- [ ] Console errors 0; links 0 broken; forms and builders exercised; no frozen page.
- [ ] Hard facts grepped everywhere after any change, cards and schema included.
- [ ] Anti-generic fingerprint 3 or under; swap test and blocker test pass ([03-structure.md](03-structure.md)).
- [ ] Above the fold painted; no-JS net; reduced-motion path with SVG strokes visible; the animation lint passes.
- [ ] Effects pages: poster vs live 0 px, CLS 0 on load and reload, fps measured ([06-premium-effects.md](06-premium-effects.md)).
- [ ] After deploy: live = build, purge done, `HIT`.
- [ ] Delivery audit against the proposal, the calendar and the checklist.
